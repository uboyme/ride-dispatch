## 迭代记录

### 2026-11-24 超时重派

处理两种情况：

1. **派出去了，司机不理**：订单"已派单"超过 15 秒没人接 → 订单退回待派单，记一条超时拒单，司机设为离线，然后换人重派。
2. **一直派不出去**：订单停在"待派单" → 每轮扫描重试派单；下单超过 5 分钟仍派不出去，系统自动取消（取消方为系统，免费）。

| 修改 | 文件 |
|---|---|
| 新增定时任务，每 5 秒扫描一轮 | 新增 `job/DispatchJob.java`，启动类加 `@EnableScheduling` |
| 新增 `handleAcceptTimeout()`、`systemCancel()` | `service/OrderService.java` |
| 派单时记录派单时间 `dispatched_at` | `entity/RideOrder.java`、`service/DispatchService.java` |
| 超时秒数、放弃派单分钟数、扫描间隔改为配置项 | `application.yml`、`config/RideDispatchProperties.java` |
| 建表语句放进仓库 | 新增 `sql/schema.sql` |

**设计说明**

- **为什么要新加 `dispatched_at`**：判断"派出去多久了"需要派单时间。`created_at` 是下单时间，订单被拒、重派之后就对不上了。
- **超时的司机设为离线，而不是放回空闲**：司机不响应多半是没信号或人走开了。放回空闲的话，系统会不停给他派单，每单都白等 15 秒。以后可以细化为"连续超时几次才强制下线"。
- **超时和接单撞车**：司机恰好在第 15 秒点接单，同时定时任务在处理超时。两边都以"订单状态 = 已派单"为条件更新，只有一个能成功：接单赢了，超时处理直接返回；超时赢了，司机看到"当前订单不能接单"。不需要加锁。
- **超时处理和重派分开**：超时处理只把订单退回待派单，不在同一个方法里重派。每轮扫描先处理超时、再重试待派单的订单，所以退回的订单在同一轮就会被重新派出。这样超时处理的事务里只有 MySQL 操作，不会把 Redis 卷进去。
- **用上了联合索引**：重试派单的查询是 `status = 待派单 ORDER BY created_at`，正好命中 `idx_status_created`。
- **单个订单出错不影响整批**：循环里每个订单单独 try-catch，失败的下一轮再试。
- **以后的演进**：定时扫描最多有 5 秒延迟，扫得越勤数据库压力越大。v3 计划换成延迟消息，到点精确触发。

**验证方式**

1. 先执行数据库变更（见"数据库变更记录"），再启动项目。
2. 接单超时：复位司机 → 上线 → 下单（订单 20）→ 什么都不做，等 20 秒左右 → 订单退回 10、`driver_id` 为空；`order_reject` 多一条 `reason = 2` 的记录；司机 `status = 0`。
3. 系统取消：找一个待派单的订单，执行 `UPDATE ride_order SET created_at = NOW() - INTERVAL 10 MINUTE WHERE id = 订单号;`，等几秒 → 订单 `status = 80`，`cancel_by = 3`，取消原因"长时间无司机接单"。
4. 重试派单：下单时没有司机在线（订单停在 10）→ 让司机上线 → 几秒后订单自动派给他（status 20）。

### 2026-11-24 事务修复与派单拆分

| 修改 | 文件 | 原因 |
|---|---|---|
| 订单主键改为数据库自增 | `entity/RideOrder.java` | 原来没有 `@TableId`，MyBatis-Plus 默认用雪花算法生成 19 位 id，前端 JavaScript 处理超过 16 位的整数会丢失精度 |
| `accept`、`reject`、`complete`、`cancel` 加 `@Transactional` | `service/OrderService.java` | 这几个方法会连续写多次数据库，中途失败会留下"一半成功一半失败"的数据 |
| 派单逻辑拆到 `DispatchService` | 新增 `service/DispatchService.java`，修改 `OrderService.java` | 原来 `create()` 在同一个类里调用 `dispatch()`，绕过了 Spring 代理，事务不生效。锁定司机成功、更新订单失败时，司机会卡在"已派单" |
| 数据库密码改为环境变量读取 | `application.yml` | `${DB_PASSWORD:123456}`：部署时用环境变量传入真实密码，避免提交到公开仓库 |
| 修正一行注释 | `OrderService.java` | 取消费规则的注释 |

**设计说明**

- `create()` 本身不加事务：订单先落库，派单失败时订单停在待派单，由定时任务重试。
- `reject()` 有事务，它调用的 `dispatch()` 会加入同一个事务一起提交。
- Redis 的 GEO 操作不会随 MySQL 事务回滚。如果事务回滚了，司机在 MySQL 里是空闲，但已经被移出 GEO，靠他下次上报位置时自动补回。
- 之后写超时重派的定时任务时，要调用 `dispatchService.dispatch()`。

**验证方式**

1. 重启项目，下单后返回的订单 id 应该是普通的自增数字，而不是 19 位长数字。
2. 重跑回归测试：上线 → 下单 → 接单 → 行程推进 → 完成；拒单；取消（已派单、接单超时、司机已到达、行程中）。
3. 不设置环境变量时，项目仍能用默认密码 `123456` 连上本地数据库。

### 2026-11-23 魔法值重构 + 取消订单

- 订单状态、司机状态、服务类型、取消方、拒单原因改为枚举，代码 `@EnumValue` 存数据库、`@JsonValue` 返回前端，表结构不变。
- 状态判断封装成语义化方法：`OrderStatus.canCancel()`、`hasFreeCancellationWindow()`。
- 取消费、免费取消分钟数、派单半径、候选司机数、GEO key 前缀移到 `application.yml`（`RideDispatchProperties`）。
- 新增取消订单，规则：

| 订单状态 | 乘客取消 |
|---|---|
| 待派单、已派单 | 免费 |
| 已接单、接驾中 | 接单 3 分钟内免费，超过收 5 元 |
| 司机已到达 | 直接收 5 元 |
| 行程中及之后 | 不能取消 |

- 取消用"状态等于刚才读到的状态"做条件更新，保证收费金额和状态对得上。
- 规则修正：最初写成"司机到达后等待 5 分钟内免费取消"，把"乘客取消"和"司机免费等待"两件事混在一起了。修正为司机到达后取消直接收费；"免费等待 5 分钟、超时收等待费或司机无责取消"留到以后做。

### 2026-11-23 行程推进

- 出发、到达、上车、完成四个接口，每一步都用 `status = 原状态 AND driver_id = 本人` 做条件更新，防止跳步和别的司机操作。
- 到达、上车、完成抽成通用方法 `advance()`，传入"从哪个状态到哪个状态、记哪个时间字段"。
- 完成后司机恢复空闲；不手动写回 GEO，下次位置上报时自动加入。

### 2026-11-22 下单、派单、接单、拒单

- 下单后立即贪心派单：以起点为圆心 GEOSEARCH 3 公里内最近的 10 个司机，排除拒过这一单的，按距离依次用条件更新锁定司机，成功一个就停。
- **Redis 推荐候选，MySQL 做最终裁决**：GEO 数据可能滞后（司机刚下线、刚被别的订单抢走），以 MySQL 条件更新结果为准。
- 锁定司机后如果订单已被取消（更新订单影响 0 行），把司机放回空闲。
- 拒单写入 `order_reject`，订单退回待派单并重新派单。

### 2026-11-22 司机上线、下线、位置上报

- GEO 只存空闲司机：上线时加入，被派单或下线时移除。
- 位置上报时只要司机在 MySQL 里是空闲，就重新 GEOADD。上线时 Redis 写失败，最多一个上报周期后自动修复，不需要分布式事务。

## 关键设计决策

| 决策 | 原因 |
|---|---|
| 用条件更新（乐观锁）保证并发安全，不用分布式锁 | 抢同一个司机的请求很少，一条带状态条件的 UPDATE 就够，简单可靠 |
| GEO 只存空闲司机 | 查出来的司机天然可派；Redis 与 MySQL 不一致时靠位置上报自动修复 |
| 订单状态值用 10、20、30 | 以后在中间插入新状态时还有空位 |
| 取消只有一个"已取消"状态，取消方和原因用字段记录 | 避免状态数量爆炸 |
| 派单逻辑独立成 `DispatchService` | 让调用经过 Spring 代理，事务生效 |
