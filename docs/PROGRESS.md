### 2026-11-28 司机模拟器

写了一个独立运行的模拟器，扮演多个司机 App 和乘客，通过 HTTP 调用后端接口，自动跑完整的业务流程。

**每个司机**（一个虚拟线程）循环执行：上报位置（每 3 秒，位置随机小幅移动）→ 查询有没有派给自己的新单 → 有的话按概率决定：70% 接单并跑完全程（出发 → 到达 → 上车 → 完成），15% 拒单，15% 不理（等超时）→ 每 5 轮检查一次自己是否被系统设为离线，是的话重新上线。

**乘客**：每 2 秒在中心点附近随机下一单。

| 修改 | 文件 |
|---|---|
| 新增接口：查询司机当前进行中的订单（司机端轮询用） | `DriverController.java`：`GET /drivers/{id}/current-order`；`OrderService.currentOrderOfDriver()` |
| 模拟器 | 新增 `src/test/java/.../simulator/DriverSimulator.java` |
| 模拟时临时关闭 SQL 日志 | `application.yml` 注释掉 `log-impl` |

**设计说明**

- **为什么要新加"查询当前订单"接口**：模拟器和真实的司机 App 一样，只能通过接口和后端交互，不能直接查数据库。原来没有任何接口能让司机知道"有一单派给我了"。
- **轮询，而不是推送**：真实 App 是服务端通过长连接（如 WebSocket）主动推送订单。v1 用轮询，简单，但有代价：1000 个司机每 3 秒查一次，就是每秒 300 多次查询，绝大多数答案是"没有"。这是 v2 压测要观察的点，也是以后改成推送的理由。
- **放在 `src/test/java`**：它是测试工具，打包部署时不会进入 jar。
- **为什么不直接用 JMeter**：JMeter 适合对单个接口压测；司机的行为是有状态的，要根据派单结果决定下一步，用代码写成循环更清楚。v2 两者分工：JMeter 测单接口极限，模拟器做端到端业务压测。
- **几个并发细节**：`volatile` 的运行开关保证所有线程能及时看到停止信号；统计用 `AtomicInteger` 避免并发计数丢失；格式化小数用 `Locale.ROOT`，避免某些语言环境把小数点写成逗号；司机记下自己决定不理的订单号，避免下一轮重新决定。

**第一次运行结果**（10 个司机，2 分钟）

```
下单 59｜接单 47｜接单失败 0｜拒单 13｜不理 14｜完成 47｜重新上线 11｜出错 0
```

- 接单 + 拒单 + 不理 = 74，多于下单数 59：被拒、超时的订单改派给了其他司机，一单可能被决定多次
- 接单、拒单、不理的比例（64% / 18% / 19%）和设定的概率（70% / 15% / 15%）基本一致
- 不理 14 次、重新上线 11 次：超时下线 → 重新上线的路径走通了
- **正确性检查**：模拟结束后查询"同一司机同时有多单在进行"，结果为空，并发派单下没有出现重复派单

**运行方式**：先启动后端，再运行 `DriverSimulator.main()`。运行前清空订单表和拒单表、把司机都设为离线、`DEL driver:geo:1`；运行后把模拟司机设为离线、再清一次 GEO，避免影响后续手动测试。

### 2026-11-27 异常体系与参数校验

搭建项目的异常体系：所有接口返回统一格式，错误按类别返回有语义的 HTTP 状态码，参数在入口处校验。

**统一返回格式**：`{"code": 0, "message": "success", "data": ...}`。code 为 0 表示成功，其他值表示具体错误；出错时 data 为 null。

**错误分三类**

| 类别 | 例子 | HTTP | 返回的提示 |
|---|---|---|---|
| 参数错误 | 漏传 serviceType，经度填 999 | 400 | 具体哪个字段有问题 |
| 业务错误 | 订单不存在、当前状态不能取消、手机号已注册 | 404 / 409 | 业务提示 |
| 系统错误 | 数据库连不上、空指针 | 500 | 统一"系统繁忙"，详细报错只记日志 |

| 修改 | 文件 |
|---|---|
| 统一返回 `Result`、错误码 `ErrorCode`、业务异常 `BizException`、全局异常处理器 `GlobalExceptionHandler` | 新增 `common` 包 |
| 所有 `RuntimeException` 换成 `BizException`，带上错误码 | `service/DriverService.java`、`service/OrderService.java` |
| 所有接口改为返回 `Result` | 两个 Controller |
| 下单、位置上报、新增司机加参数校验，参数前加 `@Valid` | 请求对象和 Controller；`pom.xml` 引入 `spring-boot-starter-validation` |
| 新增司机改用专门的请求对象 `CreateDriverRequest`，状态固定为离线；查询和新增都挪到 `DriverService` | `DriverService.java`、`DriverController.java` |
| 数据库连接时区统一为北京时间 | `application.yml` 的 url 加 `forceConnectionTimeZoneToSession=true` |

**设计说明**

- **HTTP 状态码表示大类，code 表示具体错误**：错误码前三位就是 HTTP 状态码，如 40902 = 409 冲突类的第 2 种。
- **全局异常处理用 `@RestControllerAdvice`，不用 AOP**：参数解析、校验、路径匹配阶段的异常发生在 Controller 方法执行之前，AOP 切面接不到；DispatcherServlet 用 try-catch 包住了整个请求过程，都能接住。
- **40000 不是业务代码抛的**：校验失败、JSON 写错、缺参数、参数类型不对，都是 Spring 框架抛出的异常，由全局异常处理器统一翻译成 `PARAM_INVALID`。
- **经纬度用 `Double` 而不是 `double`**：基本类型漏传时默认是 0，校验发现不了，司机会被定位到经纬度 (0, 0)；包装类型漏传是 null，`@NotNull` 能拦住。
- **校验注解都显式写 message**：内置提示会跟随运行机器的语言变化，中文系统是"不能为null"，英文服务器上会变成 "must not be null"。
- **手机号重复靠唯一索引兜底，捕获 `DuplicateKeyException`**：先查后插在并发下仍可能两个都通过检查，第二个插入还是会失败，所以无论如何都要捕获异常；捕获之后，先查就多余了。
- **review 中补上的两个漏洞**：手机号重复、请求体不是 JSON，原来都会落进兜底返回 500。现在分别返回 409"手机号已注册"和 415"请求体必须是 JSON 格式"。

**验证方式**

| 请求 | 预期 |
|---|---|
| 下单漏传 serviceType | 400，"serviceType 不能为空" |
| 下单 startLng 填 999 | 400，"startLng 必须在 -180 到 180 之间" |
| 上线 Body 只传 lat | 400，"lng 不能为空" |
| 新增司机用已注册的手机号 | 409，"手机号已注册" |
| 新增司机时 Body 里带 `"status":1` | 新司机的 status 仍是 0 |
| GET `/orders/1/accept`、POST `/abc` | 405、404 |
| 已在线的司机再上线 | 409，"当前状态不能上线" |

### 2026-11-24 超时重派

处理两种情况：

1. **派出去了，司机不理**：订单"已派单"超过 15 秒没人接 → 订单退回待派单，记一条超时拒单，司机设为离线，然后换人重派。
2. **一直派不出去**：订单停在"待派单" → 每轮扫描重试派单；下单超过 5 分钟仍派不出去，系统自动取消（取消方为系统，免费）。

| 修改 | 文件 |
|---|---|
| 新增定时任务，每 5 秒扫描一轮 | 新增 `job/DispatchJob.java`，启动类加 `@EnableScheduling` |
| 新增 `handleAcceptTimeout()`、`systemCancel()` | `service/OrderService.java` |
| 派单时记录派单时间 `dispatched_at` | `entity/RideOrder.java`、`service/DispatchService.java` |
| 超时秒数、放弃派单分钟数、扫描间隔改为配置项 | `application.yml`、`config/RideDispatchProperties.java` |
| 建表语句放进仓库 | 新增 `sql/schema.sql` |

**设计说明**

- **为什么要新加 `dispatched_at`**：判断"派出去多久了"需要派单时间。`created_at` 是下单时间，订单被拒、重派之后就对不上了。
- **超时的司机设为离线，而不是放回空闲**：司机不响应多半是没信号或人走开了。放回空闲的话，系统会不停给他派单，每单都白等 15 秒。以后可以细化为"连续超时几次才强制下线"。
- **超时和接单撞车**：司机恰好在第 15 秒点接单，同时定时任务在处理超时。两边都以"订单状态 = 已派单"为条件更新，只有一个能成功：接单赢了，超时处理直接返回；超时赢了，司机看到"当前订单不能接单"。不需要加锁。
- **超时处理和重派分开**：超时处理只把订单退回待派单，不在同一个方法里重派。每轮扫描先处理超时、再重试待派单的订单，所以退回的订单在同一轮就会被重新派出。这样超时处理的事务里只有 MySQL 操作，不会把 Redis 卷进去。
- **用上了联合索引**：重试派单的查询是 `status = 待派单 ORDER BY created_at`，正好命中 `idx_status_created`。
- **单个订单出错不影响整批**：循环里每个订单单独 try-catch，失败的下一轮再试。
- **以后的演进**：定时扫描最多有 5 秒延迟，扫得越勤数据库压力越大。v3 计划换成延迟消息，到点精确触发。

**验证方式**

1. 先执行数据库变更（见"数据库变更记录"），再启动项目。
2. 接单超时：复位司机 → 上线 → 下单（订单 20）→ 什么都不做，等 20 秒左右 → 订单退回 10、`driver_id` 为空；`order_reject` 多一条 `reason = 2` 的记录；司机 `status = 0`。
3. 系统取消：找一个待派单的订单，执行 `UPDATE ride_order SET created_at = NOW() - INTERVAL 10 MINUTE WHERE id = 订单号;`，等几秒 → 订单 `status = 80`，`cancel_by = 3`，取消原因"长时间无司机接单"。
4. 重试派单：下单时没有司机在线（订单停在 10）→ 让司机上线 → 几秒后订单自动派给他（status 20）。

### 2026-11-24 事务修复与派单拆分

| 修改 | 文件 | 原因 |
|---|---|---|
| 订单主键改为数据库自增 | `entity/RideOrder.java` | 原来没有 `@TableId`，MyBatis-Plus 默认用雪花算法生成 19 位 id，前端 JavaScript 处理超过 16 位的整数会丢失精度 |
| `accept`、`reject`、`complete`、`cancel` 加 `@Transactional` | `service/OrderService.java` | 这几个方法会连续写多次数据库，中途失败会留下"一半成功一半失败"的数据 |
| 派单逻辑拆到 `DispatchService` | 新增 `service/DispatchService.java`，修改 `OrderService.java` | 原来 `create()` 在同一个类里调用 `dispatch()`，绕过了 Spring 代理，事务不生效。锁定司机成功、更新订单失败时，司机会卡在"已派单" |
| 数据库密码改为环境变量读取 | `application.yml` | `${DB_PASSWORD:123456}`：部署时用环境变量传入真实密码，避免提交到公开仓库 |
| 修正一行注释 | `OrderService.java` | 取消费规则的注释 |

**设计说明**

- `create()` 本身不加事务：订单先落库，派单失败时订单停在待派单，由定时任务重试。
- `reject()` 有事务，它调用的 `dispatch()` 会加入同一个事务一起提交。
- Redis 的 GEO 操作不会随 MySQL 事务回滚。如果事务回滚了，司机在 MySQL 里是空闲，但已经被移出 GEO，靠他下次上报位置时自动补回。
- 之后写超时重派的定时任务时，要调用 `dispatchService.dispatch()`。

**验证方式**

1. 重启项目，下单后返回的订单 id 应该是普通的自增数字，而不是 19 位长数字。
2. 重跑回归测试：上线 → 下单 → 接单 → 行程推进 → 完成；拒单；取消（已派单、接单超时、司机已到达、行程中）。
3. 不设置环境变量时，项目仍能用默认密码 `123456` 连上本地数据库。

### 2026-11-22 下单、派单、接单、拒单

- 下单后立即贪心派单：以起点为圆心 GEOSEARCH 3 公里内最近的 10 个司机，排除拒过这一单的，按距离依次用条件更新锁定司机，成功一个就停。

- 拒单写入 `order_reject`，订单退回待派单并重新派单。

### 2026-11-22 司机上线、下线、位置上报

- GEO 只存空闲司机：上线时加入，被派单或下线时移除。
- 位置上报时只要司机在 MySQL 里是空闲，就重新 GEOADD。上线时 Redis 写失败，最多一个上报周期后自动修复，不需要分布式事务。

## 关键设计决策

| 决策 | 原因 |
|---|---|
| 用条件更新（乐观锁）保证并发安全，不用分布式锁 | 抢同一个司机的请求很少，一条带状态条件的 UPDATE 就够，简单可靠 |
| GEO 只存空闲司机 | 查出来的司机天然可派；Redis 与 MySQL 不一致时靠位置上报自动修复 |
| 订单状态值用 10、20、30 | 以后在中间插入新状态时还有空位 |
| 取消只有一个"已取消"状态，取消方和原因用字段记录 | 避免状态数量爆炸 |
| 派单逻辑独立成 `DispatchService` | 让调用经过 Spring 代理，事务生效 |

## 问题分析笔记

review 和讨论中得出的分析，面试时可以直接拿来讲。

### 为什么连续多次写库要加事务（以接单为例）

接单 `accept()` 要写两次数据库：

1. 订单：已派单 → 已接单
2. 司机：已派单 → 服务中

**不加事务会怎样**：程序出错时，通常是**前面成功、后面失败**，因为前一步一旦抛出异常，后面的代码根本不会执行。假设第 1 步成功、第 2 步失败：

- 订单显示"已接单"，司机却卡在"已派单"。
- 系统不会再给"已派单"的司机派新单。
- 行程完成时，代码只会把"服务中"的司机恢复空闲，也救不回他。
- 结果：**这个司机再也接不到单了**。

**加了事务**：第 2 步失败时，第 1 步跟着回滚，订单和司机的状态始终对得上。这就是事务的**原子性**（ACID 里的 A）：一组写操作要么全部成功，要么全部回滚。

**什么时候需要**：一个方法里有**两次及以上的写操作**。只有一条写 SQL 的方法（如 `depart()`）不需要，单条 SQL 本身就是原子的；只读不写的方法也不需要。

### 事务和条件更新的区别

两者解决的不是同一个问题，项目里同时用到：

| | 解决什么 | 例子 |
|---|---|---|
| 条件更新（乐观锁） | **多个请求之间**的并发冲突 | 两个订单同时抢张三，只有一个能锁定成功 |
| 事务 | **一个请求内部**多个步骤的完整性 | 接单的两次写要么都成功，要么都回滚 |

### 同类内部调用，事务不生效

Spring 的 `@Transactional` 靠**代理**实现：外部调用先经过代理，代理开启事务，再转给真正的对象。如果在同一个类里直接调用 `this.dispatch()`，这次调用没有经过代理，方法上的 `@Transactional` 就不起作用。

本项目原来 `create()` 直接调用本类的 `dispatch()`，派单时"锁定司机"和"更新订单"不在同一个事务里。锁定司机成功、更新订单抛异常时，司机会卡在"已派单"。修复方法：把派单拆成独立的 `DispatchService`，其他类通过注入调用，调用经过代理，事务生效（见 2026-11-24 迭代记录）。

补充：在一个已开启事务的方法里（如 `reject()`）调用其他方法，被调用的方法会加入同一个事务，这种情况不受影响。

### 事务管不到 Redis

`@Transactional` 只回滚 MySQL，已经执行的 Redis 操作撤不回来。所以本项目的原则是：**MySQL 是最终裁判，Redis 只负责加速查找**。Redis 和 MySQL 不一致时，靠司机定期上报位置自动修复，或者以后靠对账任务兜底。

### 排查记录：时区不一致，订单被系统误取消

**现象**：测试超时重派时，张三超时后订单没有改派给在线的李四，而是变成了"已取消"，取消原因是"长时间无司机接单"。

**排查**：拒单记录的 `created_at` 显示 12:16，而测试时北京时间是 20:16，正好差 8 小时。

**原因**：订单表的时间有两个来源，时区不一致。

| 字段 | 谁写入 | 时区 |
|---|---|---|
| `created_at` | MySQL 默认值 `CURRENT_TIMESTAMP`（`create()` 里没有设置它，MyBatis-Plus 插入时跳过 null 字段） | 按连接的会话时区计算，Docker 里的 MySQL 默认是 UTC |
| `dispatched_at` 等 | Java 的 `LocalDateTime.now()` | 北京时间 |

定时任务用 `created_at` 和 Java 的当前时间比较，算出订单"已经等了 8 小时"，超过 5 分钟上限，于是直接系统取消，根本没有去派单。而超时判断用的 `dispatched_at` 两边都是北京时间，所以张三超时是正常触发的，问题更难被发现。

**修复**：JDBC url 加上 `forceConnectionTimeZoneToSession=true`。原来的 `serverTimezone=Asia/Shanghai` 只告诉驱动"数据库用的是北京时间"，不会改数据库这一侧；加上这个参数后，驱动每建立一个连接都会把会话时区设成北京时间，`CURRENT_TIMESTAMP` 和 `NOW()` 也就都是北京时间了。

**补充**：MySQL 的时区分**全局**和**会话**两层。这个参数只改项目自己的连接，IDEA 的查询控制台是另一个连接，`SELECT NOW()` 看到的仍是 UTC。想让所有连接都一致，可以在启动 MySQL 容器时加 `--default-time-zone=+08:00`。

**教训**：

- **互相比较的时间，最好来自同一个时钟**。就算时区统一了，程序和数据库部署在不同机器上时，两台机器的时钟也可能有偏差。更严谨的做法是让数据库自己比较，比如 `WHERE dispatched_at < NOW() - INTERVAL 15 SECOND`。
- **不要让正确性依赖精确的时间**。本项目中超时和接单"撞车"时，由条件更新决定谁成功，时钟差一点只会让超时早一点或晚一点触发，不会把一单派给两个人。
- **先看日志、查数据，再下结论**。这次靠一条记录的时间差 8 小时找到了原因。

### 兜底处理器会把用户错误误判成 500

全局异常处理器遇到没有专门处理的异常，一律当系统错误，返回 500。这能保证不泄露内部信息，但用户造成的错误也会被误判：比如手机号重复（唯一索引冲突），以及请求体不是 JSON（415），最初都返回了"系统繁忙"。

误判的坏处：用户不知道该怎么改，只能反复重试；线上监控按 5xx 比例告警时，会产生假告警。

**处理方式**：上线后盯着 ERROR 日志，每出现一种新的 ERROR，判断是谁的错。框架抛出的异常（如 415）在全局异常处理器里加处理方法；带业务含义的异常（如手机号重复）在业务代码里捕获，转成 `BizException`，因为只有业务代码知道重复的是哪个字段。

**4xx 还是 5xx 的判断标准**：用户改一下请求就能成功，是 4xx；用户什么都改不了，是 5xx。
